01

概要

本ツールはエンダーアイ（Eye of Ender）の飛行軌跡を複数回記録し、各軌跡が示す方向線の交点を推定することで、エンドポータルのXZ座標を逆算する。

各投てきで「投てき前座標」と「落下地点座標」の 2 点が得られる。この 2 点を結ぶ直線の延長上にポータルが存在するという物理的事実を数学的に利用する。

エンダーアイは常にエンドポータルの方向へ飛ぶ。複数の異なる方向から投げた直線が一点に収束する場所がポータルである。

Minecraft 座標系の定義

Minecraft の座標系は独自の定義を持つ。本ツールはこの座標系に準拠して全計算を行う。

軸正方向負方向本ツールでの用途
X 軸東 (East)西 (West)ポータル計算に使用
Y 軸上 (Up)下 (Down)不使用（XZ 平面のみ）
Z 軸南 (South)北 (North)ポータル計算に使用

グラフ描画において：

  • キャンバス右方向 (+canvas X) ＝ Minecraft の +X（東）
  • キャンバス下方向 (+canvas Y) ＝ Minecraft の +Z（南）
  • 北は画面の上、南は画面の下に対応

投てき方向ベクトルの計算

入力データ

変数意味確認方法
px_i投てき前の X 座標F3 画面
pz_i投てき前の Z 座標F3 画面
lx_i落下地点の X 座標アイ着地後 F3
lz_i落下地点の Z 座標アイ着地後 F3

差分ベクトル

Δx_i = lx_i − px_i Δz_i = lz_i − pz_i

ベクトル長

len_i = √(Δx_i² + Δz_i²)
len_i < 1×10⁻⁶ の場合、投てき前と落下地点が同一とみなしその行をスキップする。

単位ベクトルへの正規化

dx_i = Δx_i / len_i dz_i = Δz_i / len_i

これにより ‖d_i‖ = 1 が保証される。

ベアリング角（表示用）

bearing_i = ( atan2(dx_i, −dz_i) × 180/π + 360 ) mod 360
北 = 0°、東 = 90°、南 = 180°、西 = 270°。時計回りに増加する。
04

重み付き最小二乗法による交点推定

問題の定式化

各投てき i は「点 q_i = (px_i, pz_i) を通り、方向 d_i = (dx_i, dz_i) に延びる直線」を定義する。

n 本の直線の最近接点 p = (X, Z) を求める問題は、以下の最小化問題として定式化される。

minimize Σᵢ wᵢ · ‖(p − qᵢ) − ((p−qᵢ)·dᵢ) dᵢ‖²

第 2 項は「p から直線への射影ベクトル」であり、全体は「p から直線 i への垂直距離の二乗」を表す。wᵢ は各投てきの重み（次節参照）。

行列形式への変換

最小化条件（偏微分 = 0）を整理すると、以下の 2×2 線形方程式になる。

A · p = b
A = Σᵢ wᵢ (I − dᵢ dᵢᵀ) b = Σᵢ wᵢ (I − dᵢ dᵢᵀ) qᵢ

行列 A と b の成分展開

(I − d dᵀ) の成分：

1−dx²
−dx·dz
−dz·dx
1−dz²
m00, m01
m10, m11

全投てきの重み付き積み上げ：

A[0][0] = Σ wᵢ·m00ᵢ A[0][1] = Σ wᵢ·m01ᵢ A[1][0] = Σ wᵢ·m10ᵢ A[1][1] = Σ wᵢ·m11ᵢ b[0] = Σ wᵢ (m00ᵢ·px_i + m01ᵢ·pz_i) b[1] = Σ wᵢ (m10ᵢ·px_i + m11ᵢ·pz_i)

連立方程式の解法（クラメールの公式）

det(A) = A[0][0]·A[1][1] − A[0][1]·A[1][0]
|det(A)| < 1×10⁻¹⁰ の場合、全直線が平行とみなし計算を中断する。
X = ( A[1][1]·b[0] − A[0][1]·b[1] ) / det(A) Z = ( A[0][0]·b[1] − A[1][0]·b[0] ) / det(A)

これが推定ポータル座標 (X, Z) の候補値となる。確定する前に、次節で物理的妥当性を検証する。

05

後入力データの優先重み付け

プレイヤーがポータルへ近づくにつれ、より後に投げたデータほど精度が高い。テーブルの下の行（後から追加した行）ほど重要度が高いと仮定し、指数的な重みを採用する。

重み関数

wᵢ = 1.5ⁱ (i は 0 始まりの行インデックス)

この重みは 最小二乗法（メイン）と レイ交点平均法（フォールバック）の両方で使用される。レイ交点法ではペア (i, j) の重みは wᵢⱼ = 1.5ⁱ × 1.5ʲ となる。

06

方向制約検証REV.3 改訂

なぜ必要か

最小二乗法は直線を 両方向に無限 に延びるものとして扱う。しかしエンダーアイは投てき前から落下地点へという 明確な向き を持ち、ポータルは必ずその「前方」に存在する。

投てきが互いにほぼ平行な場合、最小二乗法は 後方延長線が交わる点 を解として返してしまうことがある。これは数学的には正しいが、物理的にはあり得ない結果。

NG — 後方解
飛行方向と真逆に推定
OK — 前方解
飛行方向と一致

制約式（内積判定）

推定座標 (X, Z) が投てき i の前方にあるか、内積で判定する。

v_i = (X − px_i, Z − pz_i) ← 投てき前→推定点ベクトル dot_i = v_i · d_i = (X−px_i)·dx_i + (Z−pz_i)·dz_i
dot_i > 0 → 前方（物理的に妥当） dot_i ≤ 0 → 後方（物理的に不可能）
この検証は「単位ベクトルの符号情報を捨てない」ためのもの。1 本でも投てきデータがあれば、ポータルが X 軸・Z 軸のどちら側にあるかは確定する。

3 段階の判定ロジック

全 n 本の投てきについて dot_i を計算し、後方判定数 (backwardCount) と前方判定数 (forwardCount) を集計する。

PASS
backwardCount = 0（全行が前方）
→ 結果をそのまま採用
WARN
1 ≤ backwardCount < n（一部が後方）
→ 結果は採用するが、矛盾する行番号を警告で表示
FALLBACK
backwardCount = n（全行が後方）
→ 最小二乗法を 放棄し、前方制約レイ交点平均法に切替（次節）

フォールバック後の再検証

レイ交点法に切り替えた後、新しい結果に対してもう一度 dot 判定を行う。これは最終結果が物理的に妥当か確認するための保険であり、レイ交点法の加重平均が個々のペアでは前方でも、平均後の点が別の行から見て後方になり得るため必須のステップである。

  • 再検証で全行が前方 → 採用（「切り替えました」の警告付き）
  • 再検証で一部が後方 → 採用しつつ、矛盾する行番号の警告を追加
  • 再検証でも全行が後方のまま → レイ交点法も実質失敗とみなし REJECT（最終エラー）
  • レイ交点法自体が失敗（前方交差ペアが 0 件）→ 同じく REJECT
「再検証でも全行が後方」は n ≥ 3 の場合にのみ起こりうる。n = 2 では前方交点の定義上、成功したレイ交点は自動的に両方の直線にとって前方になるため、この分岐は発生しない（数学的に証明可能）。
例：4 本全てが東南東 (≈27°) を向いている入力で、最小二乗法が NW (-1003, -563) を返した場合。
検証結果 → backwardCount = 4（全行 NG）→ レイ交点平均法に切替 → 前方の SE 領域に結果を再計算
06b

前方制約レイ交点平均法REV.3 新規

アルゴリズムの位置づけ

最小二乗法が「全行と逆向き」の解を返したとき自動起動するフォールバック。直線を扱う最小二乗法と異なり、レイ（半直線）として扱うことで物理的不可能な後方解を構造的に排除する。

レイ間の前方交点

2 本のレイ R₁ = q₁ + t₁ d₁ (t₁ ≥ 0) と R₂ = q₂ + t₂ d₂ (t₂ ≥ 0) の交点を求める。

det = d₂ₓ · d₁_z − d₁ₓ · d₂_z b = q₂ − q₁ (差分ベクトル) t₁ = (d₂ₓ · b_z − d₂_z · b_x) / det t₂ = (d₁ₓ · b_z − d₁_z · b_x) / det
|det| < 1×10⁻¹⁰ → 平行とみなし null。
t₁ ≤ 0 または t₂ ≤ 0 → 後方交差なので null（前方制約違反）。

両方の t が正の場合のみ、交点座標を返す：

P = q₁ + t₁ · d₁

全ペアの重み付き平均

n 本のレイから C(n, 2) = n(n−1)/2 ペアを取り出し、それぞれ前方交点を計算。null 以外の交点を重み付きで平均する。

wᵢⱼ = 1.5ⁱ × 1.5ʲ (i < j、後の行ペアほど大きい) X = Σ (wᵢⱼ · Pᵢⱼ.x) / Σ wᵢⱼ Z = Σ (wᵢⱼ · Pᵢⱼ.z) / Σ wᵢⱼ

有効ペア数（pairCount）が 0 の場合、フォールバックも失敗 → 最終 REJECT。

最終 REJECT 時の方向推定

フォールバックも失敗した場合、ポータル位置は確定できないが「方向」だけは確定する。全投てきの単位ベクトルの平均から方位を求めユーザーに通知。

avgDx = (Σ dx_i) / n avgDz = (Σ dz_i) / n avgLen = √(avgDx² + avgDz²) avgBearing = ( atan2(avgDx/avgLen, −avgDz/avgLen) × 180/π + 360 ) mod 360
REJECT 例：投てきが完全に平行（角度差ゼロ）または交差角が極めて小さい場合。
→ 「ポータルは 東南方向 にあるが距離不明」とエラー表示し、別方向からの再投てきを促す。

収束誤差と信頼度スコア

収束誤差（重み付き平均垂直距離）

推定点 (X, Z) から各直線への垂直距離の重み付き平均を「収束誤差」とする。

r = (X − px_i, Z − pz_i) dot = r · d_i perp = r − dot·d_i ← 垂直成分 dist_i = ‖perp‖ = √(perp_x² + perp_z²)
error = Σ(wᵢ · dist_i) / Σ wᵢ

単位はブロック。値が小さいほど各直線がよく一点に集まっていることを示す。

信頼度スコア（0〜100%）

confidence = clamp( 100 − error×2 + (n−2)×8, 0, 100 )
項係数効果
100基準値最大スコア
−error × 2誤差ペナルティ誤差 1 ブロック → −2%
+(n−2) × 8データ数ボーナス3 件目以降 1 件 → +8%

投てき方向マップの描画

座標変換（ワールド → スクリーン）

Canvas（360×360 px）への変換。パディング pad = 40 px、描画半径 R = 140 px。

midX = (minX + maxX) / 2 midZ = (minZ + maxZ) / 2 span = max(maxX−minX, maxZ−minZ, 80) × 1.5 screen_x = cx + (wx − midX) / span × R × 2 screen_y = cy + (wz − midZ) / span × R × 2
span の下限 80 は、全座標が集中している場合にマップが縮退しないためのガード値。

矢印の描画（Rev.2 簡略化）

ワールド座標とスクリーン座標は同一方向の軸を共有しているため（+X=右, +Z=下）、単位ベクトル (dx, dz) を直接スクリーン座標のピクセル変位として使用できる。

arrPx = 50 ← 矢印のピクセル長（固定） tip_x = from_x + dx_i × arrPx tip_y = from_y + dz_i × arrPx arrow_angle = atan2(dz_i, dx_i) ← 矢印ヘッドの向き
スケール変換 (× scale) を矢印に適用しないことで、座標範囲が広くても狭くても常に 50 ピクセルの一定長で描画される。これにより視認性が安定する。

表示方向は「実際の記録どおり」（改訂）

過去の実装では、方向制約に違反する行の矢印を推定ポータル方向へこっそり反転させて表示していた。しかしこれは警告文（「行 X の飛行方向が矛盾しています」）と矛盾する見た目になり、データの問題を視覚的に隠してしまう欠陥だった。

廃止した処理：if (v_i · d_i < 0) then d_i ← −d_i
この反転により、矛盾行の矢印が「あたかも正しい方向を向いているか」のように見えてしまっていた。

現在の実装ではこの反転を行わず、常に実際に記録された投てき方向をそのまま描画する。方向制約に違反する行は、矢印が推定ポータル（★）から外れた方向を向いて表示されるため、警告文と矛盾なく問題を視覚的に確認できる。

グラフは「見栄えを整える」ためのものではなく、「入力データの整合性を診断する」ためのものである、という設計方針への転換。

交差角と行列式の関係

行列式 det(A) は 2 本の直線の場合「交差の鋭さ」を表す。

NG — 平行に近い
det ≈ 0 → 計算不能
OK — 直交に近い
det 大 → 安定した交点
交差角det(A) の大きさ推定精度
90°（直交）最大交点が一意・安定
45°中程度良好な精度
0°（平行）0 に近い計算不能

直交する場合の行列式（2 直線）

d₁ = (1, 0) d₂ = (0, 1) → 東と南に直交 A = (I − d₁d₁ᵀ) + (I − d₂d₂ᵀ) = [[0,0],[0,1]] + [[1,0],[0,0]] = I det(A) = 1 → 交点が一意に定まる

平行する場合

d₁ = d₂ = (1, 0) → 同じ方向 A = 2 × [[0,0],[0,1]] = [[0,0],[0,2]] det(A) = 0 → 解なし
「ほぼ平行」のケース（det ≠ 0 だが小さい）では、計算結果が後方に飛ぶ現象が頻発する。これを救済するのが STEP 5 の方向制約検証。

実装上の数値的注意点

浮動小数点精度

  • JavaScript の Number 型は IEEE 754 倍精度（53 ビット仮数部）
  • Minecraft 座標は整数〜小数 3 桁程度のため、計算上の丸め誤差は無視できる
  • 行列式の閾値 1×10⁻¹⁰ は倍精度での実用的なゼロ判定値

表示フォーマット

結果座標の表示は小数点以下 2 桁まで（末尾ゼロ省略）：

fmt(v) = parseFloat( round(v×100)/100 ).toFixed(2)

例：1234.50 → "1234.5"、1234.00 → "1234"

スパン下限保証

全座標が非常に近い場合にグラフが縮退しないよう、最低 80 ブロック相当を保証する。

span = max(maxX−minX, maxZ−minZ, 80) × 1.5

行番号の一貫性

投てき行が「投てき前と落下地点が同じ」等の理由でスキップされた場合、有効なデータだけを詰めて連番を振ると、テーブル上の表示行番号とズレが生じる。これを防ぐため、各投てきには rowNum（テーブル上の実際の表示行番号）を保持させ、詳細データ表・警告文・グラフの番号ラベルすべてでこの値を統一的に参照する。

エラー時の表示状態リセット

calculate() は呼び出しの冒頭で必ず結果カード・グラフカードを非表示にする。これにより、どのエラー分岐で処理を打ち切っても、前回の（もはや無効な）計算結果が画面に残り続けることがない。

エラーで処理を中断する直前には、それまでに蓄積した警告（行スキップの理由など）も破棄せず表示する（flushWarnings()）。例えば入力行がすべて重複座標でスキップされた場合、「データが2件未満」というエラーだけでなく、「なぜ0件になったか」の理由もあわせて提示される。
